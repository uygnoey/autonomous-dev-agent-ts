## 1. Harness Engineering とは

### 概要

**Harness Engineering** は、AIエージェントを信頼性高く実際の業務に活用するための**環境設計規律（discipline）**である。

> 「馬（AIモデル）は強力だが方向を知らない。馬具（ハーネス）がその力を正しい方向に導く。」

### コア公式

```
エージェント = モデル（Model）+ ハーネス（Harness）
```

| 主体       | 役割                              |
| ---------- | --------------------------------- |
| モデル     | 知性 — コード作成、分析、判断      |
| ハーネス   | 方向 — 制約、コンテキスト、検証、修正 |

### 登場背景（2026年）

| 時期    | 出来事                                                                                           |
| ------- | ------------------------------------------------------------------------------------------------ |
| 2025年  | AIエージェント能力実証の年                                                                       |
| 2026-02 | **OpenAI**: Codex＋ハーネスで100万行のプロダクションコードを無人生成、"Harness Engineering"を公式用語化 |
| 2026年  | 業界コンセンサス：**「エージェント自体ではなくハーネスが難しい」**                               |

### エージェント失敗の真の原因（Harness Engineering の出発点）

モデル能力不足ではなく**オーケストレーション環境の問題**：

- 多くのステップの後に方向を失う
- 失敗したアプローチを繰り返す
- セッションが切れるとコンテキストが消失
- 目標を追跡できない

> Vercel の教訓：エージェントのツールを**80%削減したら、むしろ成功率が向上**した。

### Martin Fowler の4大機能

```
① Constrain  — エージェントができることを制限
               （アーキテクチャ境界、許可ツール、スタイルルール）

② Inform     — エージェントに何をすべきか伝える
               （仕様、役割ガイドライン、アーキテクチャドキュメント、Context Engineering）

③ Verify     — エージェントが正しく行ったか確認
               （自動テスト、型チェック、リンター、コードレビュー）

④ Correct    — 間違っていた場合に修正
               （フィードバックループ、self-repair、セッション間の進行ログ）
```

### Anthropic の2エージェントハーネス（HE 最小実装参考）

```
[Initializer Agent] — 最初の1回
  git init / init スクリプト / 機能リスト / claude-progress.txt 作成

[Coding Agent] — セッションごとに繰り返し
  claude-progress.txt 読む → 現在位置確認 → 機能1つ実装
  → テスト実行 → コミット → 進行ログ更新 → セッション終了
  → 次のセッションで再開
```

## 2. adev アーキテクチャ — 正確な理解

### adev とは何か

```
adev = AI自律開発システム
      「アイデア → プロダクションコード + ドキュメント + ビジネス成果物」全体を自動化
```

### ⚠️ 核心的区別 — bun vs Claude Agent SDK

adev を理解するために最も重要な区別：

```
┌─────────────────────────────────────────────────────────────────┐
│  bun（TypeScript ランタイム）                                     │
│  役割: adev 自体のプロセス（ハーネス）を実行するランタイム        │
│  担当: adev オーケストレーターコードの実行                         │
│  対象: adev 自身（autonomous-dev-agent-ts コードベース）          │
├─────────────────────────────────────────────────────────────────┤
│  Claude Agent SDK V2（unstable_v2_createSession / prompt）       │
│  役割: 実際の開発エージェントを spawn する SDK                    │
│  担当: target project のコード作成、テスト生成/実行、ドキュメント  │
│  対象: ユーザーが作りたいプロジェクト（target project）           │
└─────────────────────────────────────────────────────────────────┘
```

つまり：

- **bun test / bunx tsc / bunx biome** → adev 自身のコード品質管理（adev 開発インフラ）
- **Claude Agent SDK エージェント** → target project のコード作成、テスト、CI 実行

### 3層構造全体

```
┌──────────────────────────────────────────────────────────────────┐
│ 第1層: Claude API（Opus 4.6）— 会話インターフェース               │
│                                                                    │
│  ユーザー ↔ Claude API 会話：                                     │
│    アイデア出し → 企画 → 設計 → 技術スタック → ドキュメントリスト │
│    → テストケース種別定義書生成（実際のコードではなくルール/カテゴリ）│
│    → ユーザー「確定」→ Contract（HandoffPackage）生成              │
│    → 構造検証 + 整合性検証 → ユーザー確認 → 第2層開始             │
│                                                                    │
│  出力: 企画書、設計書、スペック確定版、Contract、テスト種別定義書   │
├──────────────────────────────────────────────────────────────────┤
│  adev（TypeScript/Bun プロセス）= チームリーダー = ハーネス       │
│  ↓ Claude Agent SDK V2 呼び出し                                   │
├──────────────────────────────────────────────────────────────────┤
│ 第2層: Claude Agent SDK V2 — 自律開発（target project 開発）      │
│                                                                    │
│  第2層-A: 機能単位開発ループ                                       │
│    Phase FSM: DESIGN → CODE → TEST → VERIFY                       │
│    エージェント7名（Claudeインスタンス）：                         │
│      architect: 設計、モジュール構造決定（コーディング禁止）       │
│      qa: コーディング前スペック検証ゲート（コーディング禁止）      │
│      coder×N: 実際のコード作成（唯一のコーディング権限、Gitブランチ分離）│
│      tester: テストコード生成 + Bash で実行（target スタック基準） │
│      qc: 失敗の根本原因分析（コーディング禁止）                   │
│      reviewer: コードレビュー（コーディング禁止）                  │
│      documenter: イベントトリガー → spawn → ドキュメント生成 → 終了│
│                                                                    │
│  第2層-B: 統合検証                                                │
│    段階的 Fail-Fast: Step1（E2E 10万）→ Step2（1万）→ Step3（1千）│
│    → Step4（統合 100万）— バグ0まで繰り返し                       │
│                                                                    │
│  第2層-C: ユーザー確認チェックポイント                            │
│    結果物 + テスト結果報告書 → ユーザー承認 → 第3層               │
├──────────────────────────────────────────────────────────────────┤
│ 第3層: 成果物 + 継続 E2E                                          │
│    統合ドキュメント8種 + ビジネス成果物4種                         │
│    5分間隔継続 E2E → バグ発見 → 第2層再実行                       │
└──────────────────────────────────────────────────────────────────┘
```

### 開発フローの核心

```
[第1層 — Claude API]
  tester エージェントに渡す「テストケース種別定義書」生成：
  → カテゴリ12種定義、各カテゴリのルール/パターン/境界値、サンプルケース100〜200個、
    random 80%+ 比率ルール
  → 実際のテストコードは書かない（仕様のみ）

[第2層 — Claude Agent SDK]
  tester エージェント：
  → 種別定義書を読む → target project の技術スタックを把握
  → 定義書のルールに基づきテストコードを直接作成（Write ツール）
  → Bash ツールで実行（target project のテストフレームワーク使用）
  → Jest? pytest? go test? → 第1層スペックで決定した技術スタックそのまま

  TDD サイクル：
  → tester が failing テストを先に作成
  → coder が通過するよう実装
  → 1つ失敗 → 即停止 → qc 根本原因 → coder 修正 → 最初から

  CI 役割：
  → 機能完了後に統合 E2E（段階的 Fail-Fast）
  → 新機能が既存機能を壊していないか回帰検証
```

## 3. コア公式比較

### Harness Engineering 公式

```
エージェント = モデル + ハーネス
ハーネス = Constrain + Inform + Verify + Correct
```

### adev 公式

```
adev = ハーネス（TypeScript/Bun オーケストレーター）
     + Claude Agent SDK エージェント群（モデル）

adev ハーネス：
  Constrain:
    - 単方向モジュール依存性（layer-dependencies.md）
    - allowedTools リスト（エージェントごとのツール制限）
    - エージェントごとのコーディング権限分離（coder のみコーディング可）
    - Git ブランチ分離（Coder×N のファイル競合防止）
    - エージェント7名固定（追加/変更禁止）
    - settingSources: []（ファイルシステム設定依存の除去）

  Inform:
    - 第1層 Contract（HandoffPackage）: 企画意図 → 開発仕様
    - agent.md 7個: エージェント別役割ガイドライン（プロジェクトスペック合わせて自動生成）
    - SKILL.md: ドメイン知識注入
    - LanceDB RAG: 設計決定履歴、失敗履歴のリアルタイム検索注入
    - テストケース種別定義書: tester エージェント行動基準

  Verify:
    - tester: target project テストコード生成 + 実行（Bash ツール）
    - Fail-Fast: 1つ失敗 → 即停止（最初から再実行）
    - 4重検証: qa/qc → reviewer → 第1層意図 → adev 総合
    - Haiku → Sonnet → Opus 自動エスカレーション

  Correct:
    - qc: 根本原因1つに絞って分析 → coder に修正指示
    - failure-handler: 失敗種別分類 → 適切な Phase へ復帰
    - bias-detector: 確証バイアス/ループ/デッドロック/スコープ拡大検知 → セッション再起動
    - session-restore-orchestrator: トークン切れ後 LanceDB ベースで復元
    - bug-escalator: 第3層バグ → 第2層全ループ再実行
```

## 5. TDD / CI 実装方式比較

### Harness Engineering の TDD/CI 推奨方式

```
TDD: failing テストを先に書く → 通過するよう実装 → リファクタ
CI: コミット時に自動テスト実行 → 失敗時マージブロック
```

Harness Engineering は「TDD と CI を使え」と推奨するが、**具体的な実装方法は各自が決定**。

### adev の TDD/CI — 全体フロー

```
[第1層 — テスト種別定義書生成（実際のコードではない）]

  第1層 Claude API が生成：
  - テストカテゴリ12種（正常/境界値/例外/同時実行/大容量/異常終了など）
  - カテゴリ別ルール/パターン/境界値/入力範囲
  - サンプルケース100〜200個
  - random 比率 80%+ ルール
  - 目標数量: Unit 1万 / Module 1万 / E2E 10万+（設定可）
  - Contract に含めて → 第2層 tester エージェントに伝達

[第2層 — tester エージェントが実際のテストコードを生成 + 実行]

  tester エージェント（Claude Agent SDK V2 インスタンス）：
    ① 種別定義書を読む → target project の技術スタックを把握
       （Python → pytest、TypeScript → Jest/Vitest、Go → go test など）
    ② 定義書のルールに従いテストコードを直接作成（Write ツール）
       - Unit テスト: 関数/メソッド単位
       - Module テスト: モジュール間統合
       - E2E テスト: 実際のユーザーシナリオ全ライフサイクル
    ③ Bash ツールで実行：
       `pytest tests/` または `jest` または `bun test` — スペック決定技術スタック
    ④ Fail-Fast: 1つ失敗 → 即停止 → qc に報告

[TDD サイクル]
  tester: failing テスト作成
  coder: 通過するよう実装（対象モジュール Git ブランチ）
  tester: 再実行 → 通過確認
  → Unit 全通過 → Module 開始 → Module 通過 → E2E 開始

[CI 役割 — 統合 E2E 段階式（第2層-B）]
  全機能開発完了後：
  Step1: 修正機能 E2E 10万+（機能完成度確認）
  Step2: 関連機能 E2E 1万（回帰: 他の機能が壊れていないか）
  Step3: 非関連機能 E2E 1千（スモーク: システム全体影響）
  Step4: 統合最終 E2E 100万回（プロダクションシミュレーション）
  各 Step 失敗 → 即停止 → 第2層-A 全ループ再実行（architect から）
```

| 項目              | HE 推奨                       | adev 実装                                         |
| ----------------- | ----------------------------- | ------------------------------------------------- |
| テスト仕様生成    | 開発者が直接                  | **第1層 Claude API が種別定義書を自動生成**       |
| テストコード生成  | 開発者が直接                  | **tester エージェントが種別定義書基準で自動生成** |
| テスト実行        | CI ツール（Jenkins など）     | **tester エージェントが Bash ツールで直接実行**   |
| テストフレームワーク | チームが決定               | **layer1 スペックで決定された技術スタックそのまま** |
| TDD 順序          | 推奨（実際の遵守率は低い）    | **強制（tester → coder 順序固定）**               |
| 失敗処理          | 開発者が分析                  | **qc エージェントが自動根本原因分析**             |
| CI 規模           | コミットごとのテスト          | **機能ごとに Unit 1万 + Module 1万 + E2E 10万**   |
| 統合検証規模      | デプロイパイプライン          | **段階式最終 100万回**                            |
| 回帰テスト        | CI パイプライン               | **Step2（関連機能 1万）+ Step3（非関連 1千）自動** |

## 6. エージェントオーケストレーション比較

### Anthropic HE 推奨: 2エージェント線形構造

```
Initializer → [Coding Agent × 機能数] 順次
セッションごとに1機能、progress.txt で状態引き継ぎ
```

### LangChain DeepAgents: 階層型構造

```
Main Agent
  └─ Sub-agents（必要時に動的生成）
     Filesystem / Planning / Memory / Code Exec
```

### adev: Phase FSM + 役割分離 + 並列開発

```
adev（TypeScript/Bun）= チームリーダー = オーケストレーター
  │
  ├─ DESIGN Phase [Agent Teams 有効化]
  │    session.stream() + CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1
  │    → リードエージェントが TeamCreate → architect、qa、coder、reviewer を teammate として spawn
  │    → SendMessage でチームディスカッション（設計意思決定）
  │    → qa ゲート通過 + 全員合意 → CODE Phase へ移行
  │    → 終了時に documenter トリガー（設計ドキュメント生成）
  │
  ├─ CODE Phase [Agent Teams なし、並列独立実行]
  │    unstable_v2_prompt() × N（Promise.allSettled）
  │    → coder1: feature/機能名-モジュールA-coder1 ブランチ
  │    → coder2: feature/機能名-モジュールB-coder2 ブランチ
  │    → coderN: feature/機能名-モジュールN-coderN ブランチ
  │    architect + reviewer: 別セッションで監督（コーディング禁止）
  │    → 依存関係グラフ順に adev がマージ
  │    → 完了時に documenter トリガー（CHANGELOG 更新）
  │
  ├─ TEST Phase [Fail-Fast 順次]
  │    unstable_v2_prompt() 順次実行
  │    → tester: 種別定義書基準でテストコード生成（Write ツール）
  │               Bash ツールで target project テスト実行
  │               Unit 1万 → （失敗即停止）→ Module 1万 → E2E 10万
  │    → qc: 失敗時に根本原因1つ分析
  │    → coder: 該当バグのみ修正（Fail-Fast: 1つのみ）
  │    → tester: 該当段階を最初から再実行
  │    → 完了/失敗時に documenter トリガー（テスト結果報告書）
  │
  └─ VERIFY Phase [4重検証 順次]
       unstable_v2_prompt() 順次
       ① qa/qc: スペック準拠 + テスト通過検証
       ② reviewer: コード品質 + パターン準拠
       ③ 第1層 Claude API: 「私が意図した通りに実装されたか？」
       ④ adev: 上記3つを総合 + 確証バイアスチェック
       失敗 → 種別に応じて DESIGN/CODE/TEST に復帰
```

| 項目          | Anthropic 2エージェント | LangChain DeepAgents | adev                                    |
| ------------- | ----------------------- | -------------------- | --------------------------------------- |
| エージェント数 | 2名                    | 可変                 | 7名固定                                 |
| 構造          | 線形順次                | 階層型               | Phase FSM                               |
| 並列開発      | なし                    | 部分的               | Coder×N Promise.allSettled              |
| Git 分離      | なし                    | なし                 | feature ブランチ + 依存順マージ         |
| チームディスカッション | なし           | なし                 | DESIGN Phase Agent Teams                |
| バイアス検知  | なし                    | なし                 | bias-detector（ループ/デッドロック/確証バイアス）|
| 意図検証      | なし                    | なし                 | 第1層が企画意図 vs 実装を比較            |
| 監視方法      | なし                    | なし                 | Hook（PreToolUse/PostToolUse）+ IPC ポーリング |

## 7. コンテキスト & メモリ比較

### Anthropic HE: claude-progress.txt

```
[完了] feature-1: ユーザー認証
[進行中] feature-2: 商品一覧（50%）
[未完] feature-3: 決済
```

- 利点: シンプル、人間も読める
- 限界: テキスト解析、型なし、過去パターン検索不可、トークン無駄

### adev: LanceDB 4テーブル + RAG

| テーブル            | 保存内容                   | 活用タイミング                         |
| ------------------- | -------------------------- | -------------------------------------- |
| `memory`            | ユーザー会話履歴、フィードバック、決定事項 | 次の会話コンテキスト              |
| `code_index`        | target project コードベクター | コード検索、重複防止                  |
| `design_decisions`  | 「なぜこう設計したか」履歴  | 一貫性維持、同じ決定の再検討防止       |
| `failures`          | 失敗原因 + 解決策ベクター   | 再発防止 — 類似状況の RAG アラート    |
| `session_snapshots` | セッション状態（スペック外追加） | トークン切れ後の正確な復元         |

**動的コンテキスト注入フロー**：

```
エージェント作業開始
  → 現在のコンテキストをベクター化
  → LanceDB 類似度検索：
      design_decisions で類似設計決定を検索
      failures で類似失敗履歴を検索
      code_index で関連コードを検索
  → 検索結果をエージェントプロンプトに動的注入
  → エージェントが過去の学習パターンを参照してより良い決定
```

| 項目           | HE progress.txt     | adev LanceDB                            |
| -------------- | ------------------- | --------------------------------------- |
| 保存形式       | テキスト            | ベクター DB（型安全）                   |
| 過去パターン検索 | 不可              | 類似度検索（意味ベース）                |
| 失敗再発防止   | なし                | failure-store → RAG アラート            |
| 設計一貫性     | なし                | design-decision-store → 過去の決定参照  |
| トークン効率   | ファイル全体ロード  | 関連項目のみ検索して注入                |
| 永続性         | ファイル（揮発可能）| 組み込み DB（構造的永続）               |

## 8. セッション継続性比較

### HE の核心問題: 「セッションが切れると全コンテキストが消失」

Anthropic の解法：

```
各 Coding Agent セッション開始時：
  1. claude-progress.txt を読む → 現在位置を把握
  2. 機能1つのみ実装
  3. 完了 → ログ更新 → セッション終了
  4. 次のセッションで同じ手順を繰り返し
```

### adev のセッション継続性戦略

```
[トークン上限到達時 — token-monitor.ts]
  残り 20% → 新しいセッション spawn を抑制（進行中のもののみ完了）
  残り 5%  → graceful 完了モード（新しい作業開始禁止）
  トークン消耗 → token-wait-loop.ts: 1分おきにチェック、最大1時間待機

[セッション復元 — session-restore-orchestrator.ts]
  1. session-snapshot-store から最後のスナップショットをロード
  2. unstable_v2_resumeSession(sessionId) を試みる
  3. 復元失敗時: 新セッション + LanceDB ベクターコンテキスト再構成
  4. 中断した地点から正確に再開

[セッション ID 体系]
  {projectId}:{featureId}:{agentName}:{phase}
  例: "proj-001:feat-auth:architect:DESIGN"
  → どのプロジェクトのどの機能のどのエージェントがどの Phase かを追跡
```

## 9. 共通点

### 1. 核心哲学: 「モデルよりハーネスが難しい」

- HE: エージェントの失敗はモデル能力不足ではなくオーケストレーション環境の問題
- adev: 201ファイル、32,681行のほとんどがハーネス（オーケストレーション）コード

### 2. セッション間コンテキスト継続性が必須

- HE（Anthropic）: `claude-progress.txt` でセッション引き継ぎ
- adev: `session-snapshot-store` + LanceDB + `unstable_v2_resumeSession`

### 3. 制約が自由より成果を高める

- HE（Vercel）: ツール80%削減で成功率向上
- adev: 役割別コーディング権限分離、Phase別 allowedTools 制限、エージェント7名固定

### 4. TDD + Fail-Fast が必須

- HE: TDD と速いフィードバックループを核心として推奨
- adev: tester → coder 順序強制、1つ失敗 → 即停止、最初から再実行（厳格適用）

### 5. Git ベースの作業単位

- HE（Anthropic）: 機能1つ → コミット → セッション終了
- adev: 機能1つ → feature/{機能}-{モジュール}-coderN ブランチ → 依存順マージ

### 6. 仕様（Spec）がエージェント行動の基準

- HE: 「エージェントに明確な仕様を提供せよ」
- adev: Contract（HandoffPackage）— 機能リスト、受け入れ条件、入出力型、テスト種別定義書すべて含む

### 7. 役割分離

- HE（LangChain）: Main agent + Sub-agents の役割分離
- adev: 7名のエージェントによる厳格な役割分離（混用絶対禁止）

### 8. コンテキストエンジニアリング

- HE: 正しいコンテキスト提供 = エージェントパフォーマンスの核心
- adev: agent.md（役割ガイドライン）+ SKILL.md（ドメイン知識）+ LanceDB RAG（動的）

### 9. 自己修正（Self-repair）

- HE: 失敗 → 根本原因分析 → 再試行
- adev: qc（根本原因1つに集中）+ failure-handler（種別別 Phase 復帰）

### 10. マルチプロジェクト分離

- HE: プロジェクト別ハーネス設定を推奨
- adev: `projects.json` + `.adev/` 分離 + 設定優先順位（プロジェクト > グローバル）

## 10. 相違点 — 核心的差異

### 最も根本的な違い: 方法論 vs 実装体

```
Harness Engineering:   「エージェントハーネスをどう設計すべきか」— 原則/パターンを提示
adev: HE 原則 + それ以上を実際の TypeScript コードで実装した完成システム
```

### 主要な相違点12項目

| #   | 項目               | Harness Engineering（方法論）   | adev（実装体）                              |
| --- | ------------------ | ------------------------------- | ------------------------------------------- |
| 1   | **性格**           | 原則/規律/方法論                | すぐに実行可能なソフトウェア                |
| 2   | **TDD 仕様**       | 「TDD を使え」                  | 第1層がテスト種別定義書を自動生成           |
| 3   | **TDD 実装**       | 開発者が直接                    | tester エージェントが Bash で実行           |
| 4   | **CI**             | 「CI を使え」                   | 機能ごとに最大 110,000 + 最終 100万回       |
| 5   | **企画→開発引き継ぎ** | 未定義                       | Contract（HandoffPackage）+ 位相ソート      |
| 6   | **メモリ**         | テキストファイル                | LanceDB ベクター 4テーブル + RAG            |
| 7   | **動的コンテキスト** | 未定義                        | 失敗履歴/設計決定のリアルタイム RAG 検索    |
| 8   | **検証**           | 自動化テスト1段階               | 4重検証（qa/qc → reviewer → 第1層 → adev） |

| 10  | **バイアス検知**   | 未定義                          | bias-detector（確証バイアス/ループ/デッドロック） |
| 11  | **トークン管理**   | 未解決                          | ローリングウィンドウ + graceful 完了 + セッション復元 |
| 12  | **成果物**         | コードまで                      | コード + ドキュメント8種 + ビジネス成果物4種 |

## 11. adev の強み

### 強み1: TDD を実際に強制する唯一の構造

HE は TDD を推奨するが実際の遵守率は低い。adev は **tester → coder 順序固定** で TDD を構造的に強制する。tester エージェントが failing テストを先に書かなければ、coder エージェントはコーディングを開始できない。

### 強み2: 企画意図と実装の整合性検証

HE にはない概念。4重検証の第3ステップで **第1層（企画者）が第2層（実装結果）を直接検証**する。「私が設計した通りに実装されたか？」— 単にテストが通過するだけでなく、意図が実装されたかを確認。

### 強み3: 失敗学習による自己改善

`failure-store.ts` — 失敗原因と解決策をベクターで保存。次回類似状況で RAG 検索してエージェントにアラート。**エージェントシステムは稼働するほど同じミスを繰り返さなくなる**。

### 強み4: 動的コンテキスト — HE を超越

Anthropic が推奨する progress.txt は静的だ。adev は **LanceDB 類似度検索で関連する過去の決定をリアルタイム検索して注入**する。エージェントは全履歴ではなく現在の作業に最も関連性の高いコンテキストのみを受け取る。

### 強み5: Coder×N 並列 + Git 分離

機能1つを複数の coder が並列で開発。モジュール単位で分配し、それぞれ独立した Git ブランチで作業。依存関係グラフの順序でマージ。**開発速度 N倍 + ファイル競合ゼロ**。

### 強み6: トークン上限の自動管理

長期実行エージェントシステムで最も実用的な問題。HE のどこにも解決策がない。adev は5時間ローリングウィンドウ、閾値別対応（20%、5%）、1時間待機ループ、`unstable_v2_resumeSession` で **中断なしの長期開発が可能**。

### 強み7: 確証バイアス検知

HE の Correct 原則を最も精巧に実装した部分。`bias-detector.ts` でエージェントが間違った方向を繰り返すパターン（確証バイアス、ループ、デッドロック、スコープ拡大）を検知。検知時はセッション強制終了 + 新セッションで再起動。

### 強み8: 完全ローカル実行

サーバー不要。LanceDB は組み込み（ファイルベース）。Anthropic API 以外の外部サービスなし。**データがローカルに完全保存**される。インストールは `curl one-liner` または `bun -g` 一つ。

## 12. adev の弱点 / 改善事項

### 弱点1: target project の実際の E2E 検証未実施（致命的）

**現状**: adev 自体（autonomous-dev-agent-ts）に対するテスト 204,903個は通過しているが、adev が実際の target project を自律開発する全フロー（第1層会話 → Contract → 第2層エージェント開発 → 第3層成果物）の**実際の Claude API 連携 E2E が未実施**。

- シミュレーション（モック）形式でのみ検証済み
- `adev init` + `adev start` → 実際の Claude API 呼び出しフロー未検証
- **HE の Verify 観点**: 検証の核心は「実際の環境」での検証。最も重要なものが欠けている。

### 弱点2: 7名の teammate 同時 PoC 未完了

スペック §16: 5名まで確認済み、7名同時実行未検証。

- Coder×N 並列開発で N の上限が実際どれくらいかが不確実
- HE の Constrain 観点: 制約の実際の限界が不明確

### 弱点3: PPTX/DOCX レンダラー未完成

- PPTX: コードコメント「未実装」、HTML フォールバック中
- DOCX: HTML フォールバック中
- PDF: pdfkit 未インストールで3つのテストが失敗（bun install で即解決可能）
- 第3層ビジネス成果物スペックが未完成

### 弱点4: 単一 AI プロバイダー依存

Claude Agent SDK = Anthropic 専用。GPT、Gemini、ローカル LLM のサポートなし。

- API 価格引き上げ、サービス障害時にシステム全体が停止
- HE では「ハーネスはモデルから独立すべき」という原則が示される方向性

### 弱点5: tester エージェントのテストコード品質保証が不確実

- tester エージェントが生成したテストコード自体の品質検証なし
- 「意味のないテスト」（常に pass するよう書かれたテスト）を検知するメカニズム未実装
- HE の Verify 観点: 検証ツール自体の品質保証が必要

### 弱点6: 技術スタック依存性の不透明さ

tester エージェントが Bash で実行するテストコマンドが target project 環境に依存。

- target project が特殊なテスト環境（Docker 必須、特殊 DB など）の場合、エージェントが自力で解決する必要がある
- このプロセスの失敗処理メカニズムがスペックに詳細定義不足

### 弱点7: ハーネス自体のプラグイン化未対応

MCP/Skill 拡張は可能だが、**Phase 追加、エージェント追加、検証ステップのカスタマイズが不可能**。

- HE の長期方向性: ハーネス自体が拡張可能なプラットフォームになるべき
- 現在: エージェント7名固定、Phase 4つ固定

### 弱点8: ツール最小化の再検討が必要（Vercel 原則）

Vercel: ツール80%削減で成功率向上。

- 現在 Phase 別 allowedTools 制限はあるが、各エージェントに提供するツールが最小化されているか再点検が必要
- 特に DESIGN Phase の Agent Teams 状況でのツール選択最適化の余地あり
